# 企业登录与多租户上下文

此功能在 `feat/enterprise-experience-upgrade` 上实现。`Robot_Admin` 负责身份验证后的公司选择、业务编排、会话与路由；`@robot-admin/naive-ui-components/C_Login` 仍只负责通用凭据表单和人机验证。租户／公司／角色不写入通用组件包。未接通的社区登录渠道保存在 `src/views/login/community.ts`，企业登录页不导入它。

## 演示方式

使用 Mock 模式启动 `bun run dev`，以预填的 `CHENY / 123456` 完成人机验证并登录。该账号关联两个租户下的三个公司，提交账号密码验证成功后显示已关联公司，主公司以标记推荐；点击任一公司卡片即进入，不再二次确认。页面只用一次性票据激活，不重复提交密码：

| 公司             | 归属   | 公司内角色 | 菜单效果                   |
| ---------------- | ------ | ---------- | -------------------------- |
| 江苏金恒（南京） | 主公司 | 企业管理员 | 全部演示菜单               |
| 江苏金恒（西安） | 兼任   | 运营经理   | 不包含系统管理             |
| 西安天智         | 兼任   | 只读审计   | 仅首页、仪表盘、账号和关于 |

右上角用户菜单显示当前公司与主／兼任身份，点击“切换公司”可更换上下文。首页展示项目版本、当前公司可访问的页面数和账号关联的公司数，用户管理演示列表会按公司变化。用户管理可维护账号的公司归属、唯一主公司及每个公司的角色；更改保存在当前浏览器。旧版演示目录的公司 ID 会自动迁移到新版，同时保留自定义的主／兼任及角色。`STAFF` 是单公司示例，`NOACCESS` 演示无可用公司。Mock 接受任意非空密码，拼图也仅为交互演示，**不是生产认证、人机防刷或数据隔离能力**。

## 状态与职责

1. 输入账号不会查询公司归属。首个提交直接调用 `/auth/login` 验证账号密码；失败统一提示，不透传未知账号、停用账号或原始请求报文。
2. 单个有效公司返回完整会话；多个公司只返回 `availableContexts` 和短时一次性 `loginTicket`，前端仅在页面内存中保存票据，并卸载凭据表单以清除组件持有的密码。点击公司卡片即激活，不保留密码快照，不把票据或密码放入 URL、日志及浏览器存储。改账号、重新验证或离开页面使旧票据失效。
3. 必须有且仅有一个主公司；零个公司或多个主公司都拒绝进入。主公司作为推荐项显示，登录激活用户点击的公司；认证后再次核对已授权清单，成员关系变更时拒绝已失效选择，不静默进入其他公司。角色由服务端返回，登录页不提供自行提权的角色下拉框。
4. `/auth/context/activate` 返回包含 `activeContext`、`availableContexts`、用户和上下文绑定令牌的完整会话。此时才写入状态并拉取菜单。单公司若仍返回票据，页面会自动激活该唯一公司；激活失败时保留公司卡片供直接重试。
5. `/auth/context/switch` 成功后，前端清理旧令牌、权限、动态路由和页签，再进入新公司首个可访问页面，使组件状态与在途请求无法沿用上一公司数据。请求失败则保留原会话。
6. 刷新令牌、菜单与业务接口都必须沿用当前服务端确认的上下文。前端菜单裁剪只是体验层，不是安全边界。

登录和公司激活共用完整会话入口；权限与页面就绪后，右上角仅显示一次按时段生成的欢迎，包含真实激活公司。主动退出在认证清理和登录页导航完成后显示告别；登录到期明确提示重新验证。快速退出会替换仍在显示的欢迎，不清理其他业务通知。

## 后端接入契约

类型见 `src/api/auth.contract.ts`，适配器见 `src/api/auth.ts`。新后端应实现：

- `POST /auth/login-companies`：显式发现工具接收 `{ username, password }`，密码验证成功后返回 `{ code: '0', data: { companies: [{ id, isPrimary, tenantName, companyName }] } }`。有效凭据但无成员返回空清单；未知账号或错误密码统一失败。主登录页不调用该工具，接口不授予权限、不返回角色或会话。
- `POST /auth/login`：接收账号、密码和人机验证；主页面不预先发送公司 ID。有效账号单公司直接返回 `activeContext`、完整令牌及 `availableContexts`，多公司返回短时一次性 `loginTicket` 和公司清单、无访问令牌。没有有效成员时拒绝建立会话。激活响应的公司必须与明确选择一致。
- 每个 `AuthContext` 必须提供 `isPrimary`，账号的公司清单中恰好一个为 `true`。正式用户管理接口须支持成员关系与公司内角色，由后端校验主公司唯一性、成员状态和管理员权限。演示字段不会被送入旧版 `/sys/users` 接口。
- `POST /auth/context/activate`：接收 `loginTicket`、`contextId`，服务端核验成员关系后签发上下文绑定的访问／刷新令牌。
- `POST /auth/context/switch`：接收目标 `contextId`，根据当前会话再次核验成员关系，并轮换令牌。
- `GET /auth/menu-list` 与业务接口：从已验证的会话解析租户和公司；请求中的公司 ID 只能作筛选提示，不可作授权依据。角色、菜单和数据范围均须服务端判定。

当前前端已提供 Mock 闭环与远端适配，Robot_Cloud 已配对上述认证合同；2026-10-15真实浏览器114项检查已完成，包含公司2票据激活与真实退出，详情见[Cloud验收记录](https://github.com/ChenyCHENYU/Robot_Cloud/blob/main/docs/verification-2026-10-15.md)。上线前还须覆盖跨租户资源访问、成员撤销、令牌刷新、切换并发和审计日志等服务端测试。Mock 菜单策略只在 `auth.mock.ts` 中生效，不能替代这些检查。

生产人机验证须配置 `VITE_CAPTCHA_PROVIDER=altcha`、挑战地址和验签地址，并由 `/auth/login` 服务端核验一次性挑战、过期时间与登录限流。默认本地拼图不能作为生产安全证明。

## 验证

`e2e/login-discovery.pw.ts` 在正式 remote 构建中使用隔离 HTTP fixture，覆盖无账号预发现、密码清除、仅票据激活、失败重试、唯一公司自动激活、失败统一提示和页面票据失效；这不是实际 Cloud 运行证明。共同请求和退出诊断只保留 status/code/traceId 白名单，不输出 Axios config/data/headers。

临时角色授权窗口另见 README：无偏移 `yyyy-MM-dd HH:mm:ss` 固定表示 UTC，前端提交和比较按 UTC，页面转用户本地时区显示。

运行 `bun run type-build`、`bun test --max-concurrency=1`、`bun run lint:check`、`bun run lint:eslint` 和生产／应用双模式构建。浏览器回归 `e2e/enterprise-context.pw.ts` 覆盖验证后的票据公司选择、账号变化清空、单公司直接会话、无公司拒绝、公司切换后的令牌与菜单变化；其他生产烟雾测试使用显式管理员上下文 fixture，不借用旧的无上下文令牌。

2026-10-20 登录体验回归：`bun run verify` 通过 257 项逻辑测试、109 项组件测试，以及类型、样式边界、双模式构建和体积预算检查；ESLint 保留项目已有的 10 条警告，无错误。登录发现、企业上下文、首页、登录路由和界面细节五组浏览器回归共 28 项通过，包含 390px 浅色／1657px 深色布局、点击公司直接进入、唯一公司自动激活、失败重试，以及登录欢迎和退出告别的替换。通知显示在导航栏下方，悬停也不会遮挡头像及退出入口。这轮远端登录使用隔离 HTTP fixture，未替代实际 Cloud 服务验收。
